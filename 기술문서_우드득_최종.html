3. 현재 구조 — Firebase RTDB

3-1. DB 스키마

rooms/
  {roomId}/
    state          : "waiting" | "starting" | "playing" | "finished"
    stateAndTier   : "waiting_3"      // 복합키 (단일 필드 쿼리 우회)
    hostUid        : string           // 방 생성자 UID
    startAt        : long             // 서버 절대시각 (카운트다운 동시 시작용)
    players/
      {uid}/
        uid        : string
        nick       : string
        tier       : int
        ready      : bool
        isGhost    : bool             // AI 고스트 플레이어 여부
    live/
      {uid}/
        score      : int              // 현재 점수
        combo      : int
        temperature: float            // 체온 (0이면 사망)
        alive      : bool
        spinIndex  : int
        fireLit    : bool             // 모닥불 연소 여부
    deaths/
      {uid}/
        score      : long             // 사망 시점 점수
        time       : ServerValue.Timestamp
    ranks/
      {uid}        : int              // 최종 순위 (1위 = 마지막 생존자)

activeRooms/
  {uid}            : string          // roomId — OnDisconnect 정리 추적용 (루트 레벨)

3-2. stateAndTier 복합키

Firebase RTDB는 단일 필드 쿼리만 지원. state == "waiting" && tier == 3 같은 AND 쿼리 불가.

해결책: stateAndTier = $"{state}_{tier}" 형태의 복합 문자열 필드를 유지. 매칭 시 FindWaitingRoomByTier(tier)가 이 필드를 .OrderByChild("stateAndTier").EqualTo("waiting_3")로 쿼리. 상태 변경 시 state와 stateAndTier 두 필드를 UpdateChildrenAsync 한 번에 동시 기록.

3-3. Security Rules / Index

// firebase-database-rules.json
{
  "rules": {
    "rooms": {
      ".indexOn": ["stateAndTier"],   // 복합키 쿼리 성능을 위한 인덱스
      "$roomId": {
        ".read": "auth != null",
        ".write": "auth != null"
      }
    }
  }
}

4. 핵심 클래스

4-1. RoomRepository

Firebase RTDB I/O 전담 레이어. 모든 읽기·쓰기는 이 클래스를 통한다.

메서드설명
CreateRoomWithPlayer(roomId, roomData, playerData)방 정보 + 내 플레이어 데이터 + activeRooms 5개 노드를 루트 레벨 UpdateChildrenAsync 한 번에 원자적 기록. 빈 방이 잠깐 노출되는 타이밍 제거.
FindWaitingRoomByTier(tier)stateAndTier == "waiting_{tier}" 쿼리. 정확히 내 티어 → 티어-1 → 티어+1 순서로 3단계 탐색.
SetRoomState(roomId, state, tier)state + stateAndTier 동시 업데이트 (단일 소스 유지)
UpdateLive(roomId, uid, liveData)rooms/{roomId}/live/{uid} 경로에 RoomLiveData 기록. 빈번 호출로 에러 콜백 생략.
SubscribeLive(roomId, callback)live/ 노드 전체 ValueChanged 구독. 모든 플레이어 실시간 데이터 수신.
WriteDeath(roomId, uid, score)deaths/{uid}에 score + ServerValue.Timestamp 기록
SubscribeDeaths(roomId, callback)deaths/ 구독. 변경 시 콜백으로 DataSnapshot 전달
WriteRanks(roomId, ranks)ranks/{uid} 일괄 UpdateChildrenAsync
SubscribeRank(roomId, uid, callback)ranks/{uid} 구독. UI 업데이트용
CleanupMyPreviousRoom(uid)비정상 종료 잔존 방 정리. 1차: activeRooms/{uid} 기록으로 삭제. 2차(폴백): rooms/ 전체 스캔해 내 uid가 포함된 방 삭제.

4-2. FirebaseRoomMatchSource

매칭 로직 전담. Phase 열거형(Idle → Searching → Waiting → Matched)으로 상태 관리.

멤버설명
BeginMatch()이전 잔존 방 정리(CleanupMyPreviousRoom) 후 FindWaitingRoomByTier 시작. 고스트 후보 로드 병렬 실행.
CreateNewRoom()CreateRoomWithPlayer로 방+플레이어 원자적 생성 후 EnterRoomAsHost.
JoinExistingRoom(roomId, hostUid)기존 방 참가. session.Initialize(roomId, "waiting", _myUid)로 내 UID 설정 후 JoinRoom + 구독.
IsHost (RoomSession)실제 플레이어(isGhost=false) 중 사전순 최소 uid를 호스트로 선출. 고스트를 제외해 고스트가 호스트가 되는 버그 방지.
FillWithGhosts()GhostFillTimeout 경과 + IsHost 조건 충족 시 빈자리를 고스트로 채움. 호스트만 실행해 중복 방지.
Seed (RoomSession)roomId를 SHA256 해시 후 long 변환. 모든 클라이언트가 서버 교신 없이 동일 Seed 계산 → 결정론적 랜덤 시퀀스 공유.
버그 발견 및 수정 사례 — 초기 구현에서 JoinExistingRoom이 session.Initialize(roomId, "waiting", hostUid)를 호출해 비호스트의 session.MyUid가 호스트 UID로 설정되는 버그가 있었다. 이로 인해 비호스트가 live/{hostUid}에 데이터를 써서 Firebase에 호스트 항목만 보이는 증상이 발생했다. Firebase Console에서 live 노드의 UID 항목이 1개뿐인 것을 발견하고 코드를 역추적해 원인을 확인. hostUid → _myUid 한 줄 수정으로 해결.

4-3. MatchmakingFlow

매칭 완료 후 카운트다운 → 씬 로딩 → 게임 시작 시퀀스를 담당.

// 핵심 흐름
FindWaitingRoom()
  → 방 없으면 CreateNewRoom() (원자적 생성)
  → 방 있으면 JoinExistingRoom()
  → 인원 충족 → SetRoomState("starting") → SetRoomState("playing")
  → 전 클라이언트 state 구독 수신 → 카운트다운 종료 → run.Started = true

4-4. RoomLiveSync

플레이어 상태를 0.33초 간격으로 Firebase에 기록·구독. 상대방 UI를 실시간 갱신하는 핵심 컴포넌트.

기능설명
SendMyLiveData()0.33s마다 rooms/{roomId}/live/{myUid}에 score·combo·temperature·alive·spinIndex·fireLit 전송. SlotMachine.Run에서 직접 읽어 최신값 보장.
SubscribeLive()live/ 노드 ValueChanged 구독. 수신 데이터를 _liveCache[uid]에 저장 → 상대방 패널 UI가 캐시를 읽어 렌더링.
SimulateGhosts()고스트(AI) 플레이어를 로컬에서 시뮬레이션. 체온 드레인·점수 증가를 매 틱 계산. 체온 0 도달 시 WriteDeath 기록. 호스트만 실행해 중복 방지.
GetPlayerLiveData(uid)내 데이터는 SlotMachine에서 직접 읽어 최신값 반환. 상대/고스트는 _liveCache에서 반환.

4-5. GameController — 사망/랭크 정산

사망 이벤트 수신 → Firebase 기록 → 생존자 1명 남으면 순위 산정 → WriteRanks.

// HandleMultiplayerDeath: 내 사망을 Firebase에 기록
ctx.Repository?.WriteDeath(roomId, myUid, myScore);

// OnDeathsUpdated: deaths/ 변경될 때마다 호출
private void OnDeathsUpdated(DataSnapshot snapshot, ...)
{
    if (!snapshot.Exists) return;

    // 종료 조건: 전체 인원 - 1명 사망 = 생존자 1명 남음
    if ((int)snapshot.ChildrenCount < totalPlayers - 1) return;

    // _ranksWritten 가드로 중복 기록 방지 (어느 클라이언트든 먼저 도달하면 기록)
    if (_ranksWritten) return;
    _ranksWritten = true;

    // time 기준 오름차순 정렬 → 먼저 죽은 순서 = 낮은 순위
    deaths.Sort((a, b) => a.time.CompareTo(b.time));

    // 사망자: N, N-1, ... 2위. 생존자: 1위
    ctx.Repository?.WriteRanks(roomId, ranks);
}
설계 포인트:
  • 호스트 제한 없음: 어느 클라이언트든 deaths가 totalPlayers-1에 도달하면 ranks 기록. _ranksWritten 멱등 가드로 중복 방지.
  • ServerValue.Timestamp 기준 정렬: 가장 늦게 죽은 사람이 1위 (= 최장 생존자)
  • 60초 타임아웃: 등수 미수신 시 임시 등수로 강제 확정. 영구 미저장 방지.
  • 2단계 결과 처리: 사망 직후 임시 등수로 UI 먼저 표시 → 확정 등수 수신 후 골드·DB 저장.
  • 이탈 감지: StartLifecycleWatch에서 SubscribePlayers로 로스터 감시. 이탈한 플레이어의 death를 호스트가 대필(멱등).
